# Бэклог — фидбэк руководительницы (после показа)

Дата показа: см. дату получения фидбэка.
Здесь — точные формулировки руководительницы + расшифровка, что это значит технически.

## Небольшие доработки (продолжение текущей архитектуры)

### 1. Перегенерировать вопросы
> «Возможность перегенерировать вопросы»

Кнопка «Перегенерировать» у конкретного вопроса или чанка — повторный вызов `BotHubClient.generate_questions()` с тем же текстом. Технически несложно, ложится на существующую архитектуру.

### 2. Выбор вопросов для работы/перегенерации
> «Выбрать вопросы, которые берём в работу/нужно перегенерировать»

Чекбоксы у каждой карточки вопроса в интерфейсе. Нужно доработать `st.session_state`, чтобы хранить не только сами вопросы, но и их статус отбора. Логично идёт в связке с пунктом 1 — перегенерировать можно именно отмеченные.

## Новая функция — отдельный конвейер

### 3. Загрузка готовых вопросов (не из лекции, а уже готовых)
> «Возможность загрузить вопросы свои сразу без презентации... у них есть вопросы где-то в docx/pdf/тексте, и из них необходимо сделать подходящий под ЭИОС формат»

Это не генерация — это **распознавание уже существующих вопросов** в чужом документе (docx/pdf/текст) и приведение к нашей структуре (`Question` из `src/models.py`), чтобы дальше работал тот же экспорт. Понадобится:
- Парсинг docx (можно переиспользовать похожий подход, что и с PDF)
- Промпт для BotHub: не «сгенерируй вопрос по теме», а «извлеки и структурируй уже готовый вопрос из этого текста»
- Скорее всего, свой отдельный экран в интерфейсе («Загрузить готовые вопросы» — альтернатива текущему «Загрузить лекцию»)

## Новые типы вопросов

### 4. Эссе и короткий ответ
> «Ещё два типа вопросов: Эссе и короткий ответ»

У этих типов нет единственного "правильного" варианта, как у MCQ — скорее критерии оценки/эталонный ответ для сверки. Нужно:
- Новые Pydantic-модели в `src/models.py` (`EssayQuestion`, `ShortAnswerQuestion`)
- Новые промпты в `bothub_client.py`
- Доработка всех трёх экспортёров под новые типы
- Подумать, как проверка знаний вообще работает без единственного верного ответа (скорее всего — эталонный ответ + критерии, а не автопроверка)

## Более крупный масштаб — не только код

## Новые вводные: онлайн-сессия в ЭИОС (обновление после беседы с руководителем)

**Контекст.** Вместо очной сессии — онлайн. На каждый курс преподаватель создаёт один тест из 25 вопросов.
Преподаватели кладут файлы с готовыми вопросами (Aiken, Word, PDF — «кто на что горазд») в элемент «База данных» ЭИОС.

**Процесс.** Сотрудник ИМЭС (пока единственный пользователь приложения) забирает файлы, приложение приводит их
к Aiken/XML, сотрудник проверяет и кладёт готовый файл в столбец «готовый файл» той же записи (коллеги могут
забрать вручную). Цель — положить тест в курс автоматически.

**Решения.** Вопрос не по структуре Aiken — пропускаем и уведомляем. В файле больше 25 — берём первые 25. Меньше —
сообщаем, сколько нашлось. Лекций не будет — только файлы с готовыми вопросами.

**Сделано:** режим «Тест для курса» (см. README).

**Дальше (по уровням):**
1. *Без IT:* пакетная обработка нескольких файлов; реестр готовности курсов (курс, кафедра, преподаватель, группы, статус, дата; хранить локально — ФИО); ручной выбор ответа для вопросов без пометки; проверка импорта Aiken в тестовом курсе.
2. *Токен Moodle:* забирать файлы из «Базы данных» и класть «готовый файл» обратно (проверить на тестовом курсе).
3. *Плагин на стороне Moodle:* загрузка сразу в курс. Стандартной функции API для импорта вопросов в Moodle нет; есть плагины сообщества `local_questions_importer_ws` (Moodle 4.5+) и `local_qbankremotemanager` (4.1+, умеет и создавать тест); оба принимают Moodle XML. Нужны проверка и установка программистом ИМЭС.

**Поля записи «Базы данных»** (заполняет преподаватель): ID курса, название дисциплины, кафедра (список), преподаватель (ФИО), группы, файл, срок готовности, комментарий. Ведёт приложение: статус, дата, число вопросов, ID категории/теста, ошибка. Автор записи и дата создания хранятся самой Moodle.

**Открытые вопросы:** банк вопросов или готовая активность «Тест»; версия Moodle; ответ программиста про токен и плагин; проверка Aiken-импорта в тестовом курсе; реальные файлы преподавателей для проверки.

### 5. Экспорт в разные форматы
> «Не просто выгрузка в Moodle, а в различных форматах»

> **Статус:** сделаны JSON, Excel, QTI 1.2, Moodle XML и Aiken (экспорт; чтение Aiken — в режиме «привести готовые вопросы»).

То, что мы откладывали как «QTI» — оказывается, форматов может быть несколько (под разные LMS, не только Moodle-подобные). Нужно уточнить у ИМЭС, какие конкретно системы/форматы актуальны, прежде чем реализовывать вслепую.

### 6. Прямая загрузка в ЭИОС
> «Если хочешь попробовать сразу загружать в ЭИОС, то нужно спрашивать, в какой курс, в какую категорию вопросов»

Это уже **интеграция с реальным API ЭИОС института**, не только наш код. Нужен доступ к API ЭИОС и, скорее всего, помощь программиста/IT-отдела ИМЭС — как раз то, что стоит поднять на завтрашнем совещании (см. отдельно сформулированный вопрос про архитектуру интеграции).

## Как подступаться (когда будет время)

Порядок примерно по возрастанию сложности:
1. Перегенерация + выбор вопросов (1-2) — расширение текущего интерфейса
2. Новые типы вопросов (4) — расширение схемы данных, похоже на то, что уже делали
3. Загрузка готовых вопросов (3) — новый, но самостоятельный конвейер
4. Форматы экспорта (5) — требует уточнения требований у ИМЭС
5. Интеграция с ЭИОС (6) — требует доступа к API и, вероятно, участия программиста
